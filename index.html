About

How I think about quality

I don't trust a feature because it looks done. I trust it because something provable says so — a test that fails when the behavior breaks, a SQL query that reconciles against the source of truth, a pipeline that refuses to merge red.

My background is a little unusual for QA: I've shipped full-stack .NET, written the T-SQL behind financial and lending reports, and built a personal finance app with its own CI. That means I read code as well as test it. I find the bug and I can tell you why it happened.

Lately I've been testing a newer kind of system — LLM output, where "correct" isn't binary. Checking for accuracy, consistency, and hallucinations is just quality assurance with fuzzier oracles, and I like that problem.
